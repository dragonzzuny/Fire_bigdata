# 데이터 제안 (제출 양식용)

제6회 소방안전 빅데이터 활용 및 아이디어 경진대회 · 데이터 제안
박용준 (아주대학교 산업공학과 석사과정)

**제안 유형: ☑ 융합 데이터 제안** (2개 이상의 기존·외부 데이터를 결합)

각 항목은 제출 폼에 그대로 붙일 수 있도록 500자 안에서 작성했다.
근거가 되는 실측치와 원문 인용은 뒤의 「부록」에 있다.

---

## 데이터명

```
소방대상물 통합식별키 데이터셋 (특정소방대상물·화재안전조사·건축물대장 연계)
```

---

## 데이터 설명

```
특정소방대상물, 화재안전조사, 건축물대장은 같은 건물을 다루면서도 서로 다른 번호를 쓴다. 이 데이터셋은 그 번호들을 한 줄에 모아 놓은 대조표다.

특정소방대상물 한 건마다 소방의 대상물관리번호, 국토교통부 건축물대장 관리번호, 필지고유번호(PNU), 정제한 도로명·지번주소와 좌표를 함께 싣는다. 무엇을 근거로 연결했는지와 매칭 신뢰도, 유효 시작일·종료일도 같은 줄에 넣는다.

신축·멸실 때문에 연 1회 이상 갱신이 필요하다. 유효기간을 두었으므로 특정 시점의 상태를 그대로 되살릴 수 있다. 전국이 대상이나 시·도 단위로 나누어 구축해도 된다. 파일 형태는 CSV다.
```

---

## 융합 대상 데이터 (최소 2개 · 최대 5개)

| # | 데이터명 | 보유기관 |
|---|---|---|
| 1 | 특정소방대상물 현황 | 시·도 소방본부 (플랫폼 개방 중) |
| 2 | 화재안전특별조사(점검이력) | 시·도 소방본부 (플랫폼 개방 중) |
| 3 | 건축물대장 표제부 | 국토교통부 (건축HUB·공공데이터포털 개방 중) |
| 4 | 도로명주소·건물정보 | 행정안전부 (주소기반산업지원서비스) |
| 5 | 화재발생현황 | 시·도 소방본부 (플랫폼 개방 중) |

1~3번이 핵심이다. 4번은 주소 표기 정규화에, 5번은 결합 결과 검증에 쓴다.
다섯 건 모두 이미 개방되어 있고, 없는 것은 이들을 연결하는 식별키뿐이다.

## 융합 방법

```
연결에 필요한 번호는 각 기관이 이미 보유하고 있다. 화재안전조사에는 대상물관리번호가 100% 들어 있고 건축물대장에는 전국 단일 관리번호가 있다. 특정소방대상물 데이터셋에만 둘 다 없다.

1단계는 특정소방대상물에 대상물관리번호 컬럼을 추가하는 것이다. 소방 내부 자료이므로 신규 수집 없이 점검이력과 결합된다.

2단계는 건축물대장 연계다. 소방이 보유한 건축물관리번호를 우선 쓰고, 없으면 지번주소를 PNU로 변환해 연결한다. 그래도 남으면 행정안전부 주소 API로 도로명을 정규화한 뒤 대조하고, 마지막으로 좌표 근접과 주용도 일치를 본다. 적용한 방법은 행마다 매칭근거 컬럼에 기록한다.

3단계에서 화재발생현황으로 결합 결과를 교차 확인한다. 연결하지 못한 행은 비워 둔다.
```

---

## 활용 목적 및 활용방안

```
현재는 점검이 화재를 줄이는지 측정할 수 없다. 점검이력이 어느 건물의 것인지 특정되지 않기 때문이다. 연계키가 있으면 점검받은 건물과 받지 않은 건물의 이후 화재 발생률을 비교할 수 있고, 법정 점검주기 조정과 예방 예산 성과 설명에 쓸 근거가 나온다.

점검 대상 선정 방식도 달라진다. 지금은 지역 단위로만 위험을 추정하지만 건물 단위로 내려가면 예측 단위와 점검 단위가 일치해, 예측 결과를 그대로 점검계획서로 옮길 수 있다.

플랫폼이 보유한 유동인구, 화재보험 위험도, 소방IoT 데이터도 같은 키로 대상물에 붙는다.
```

## 제안 배경 및 차별성

```
이번 대회 출품작을 개발하다 막힌 지점이다. 울산 화재안전특별조사 887,753행에는 대상물관리번호가 100% 들어 있으나, 특정소방대상물 데이터셋(컬럼 14개)에는 그 번호도 주소도 없다. 연결할 방법이 없어 88만 행을 사용하지 못했다.

애틀랜타 소방 Firebird와 뉴욕 FDNY RBIS도 같은 문제를 겪었다. 두 사례 모두 부서 간 공유되는 건물 ID가 없다는 점을 최대 난제로 지목했고, 주소 문자열 매칭으로 우회한 뒤 매칭 오류를 한계로 기록했다.

미국은 전국 단위 건물 식별자 자체가 없어 우회할 수밖에 없었다. 한국에는 건축물대장 관리번호가 이미 있다. 새로 수집하자는 제안이 아니라 각 기관이 가진 번호를 서로 알려 주자는 제안이다.
```

---

## 데이터 확보·구축 방안

```
1단계는 추가 수집 비용이 들지 않는다. 특정소방대상물 데이터셋에 대상물관리번호 컬럼을 추가하면 된다. 이 번호는 소방이 이미 쓰고 있으며, 화재안전조사 데이터에 100% 실려 있는 것이 그 근거다. 개인정보가 아닌 행정 식별자라 개방에 제약도 없다. 컬럼 하나로 점검이력 88만 행이 살아난다.

2단계 건축물대장 연계는 국토교통부 건축HUB에서 이미 개방 중인 자료를 쓴다. 건축물관리번호, PNU 변환, 행정안전부 주소 정규화, 좌표·용도 대조 순으로 적용한다.

매칭하지 못한 행은 채우지 않고 비워 둔다. 억지로 붙인 행이 섞이면 그 데이터로 만든 분석 전체가 의심받는다. 채움률보다 매칭근거 공개가 중요하다.
```

## 기대효과

```
점검의 화재 저감 효과를 측정할 수 있게 된다. 법정 점검주기 조정, 예방 예산 성과 설명, 소방시설 지원 대상 선정에 건물 단위 근거가 생긴다.

플랫폼 측면에서는 소방안전 카테고리에 240건이 등록된 반면 화재위험분석은 1건이다. 데이터를 추가하기 전에 이미 등록된 240건이 서로 결합되도록 하는 편이 활용도를 더 높인다. 이용자가 각자 주소를 정제해 매칭하던 작업이 없어지고, 같은 데이터에서 이용자마다 다른 결과가 나오는 문제도 줄어든다.

화재보험 요율 산정, 소방시설 관리업체의 대상물 이력 관리 등 플랫폼 외부 활용도 가능해진다.
```

## 기타 의견

```
출품작 개발 중 확인한 사항을 함께 적는다. 조치 비용은 크지 않다. 화재발생현황 최신 파일은 접수시각이 전부 000000이라 시간대 분석을 할 수 없다. 화재안전특별조사의 안전관리등급 컬럼은 채움률이 0%인데, 등급은 그 자체가 위험 신호다. 세종 소방용수시설은 좌표가 실린 1,792건 전부가 시 경계 밖 경북 방향을 가리켜, 모두 버리고 주소로 다시 찾았다. 대상물 데이터에는 기준일자 컬럼이 없어 과거 시점 분석에 현재 값이 섞인다. 파일명의 _0000과 _2021 구분도 명세에 없다.

이 제안이 틀릴 수 있는 지점도 밝힌다. 소방 내부에 건축물관리번호가 없을 수 있다. 그 경우에도 1단계만으로 88만 행이 살아나므로 두 단계를 분리해 제안한다.
```

## B. 국제 사례 원문

> "여러 부서에서 모은 상업용 건물 자료를 결합하기가 어렵다 — 공유되는 건물 ID
> 체계도, 일관된 주소 형식도, 자료를 정확하고 최신으로 유지하는 내부 품질관리도
> 없기 때문이다."
> — Atlanta Firebird / FDNY RBIS 사례 보고

Firebird 는 8개 자료(화재·점검이력·범죄·주류/영업허가·인구사회·상업용 부동산·
필지 상태·Google Places)를 결합했고, 그중 **점검이력**이 핵심 학습 자료였다.
본 출품작이 8개 중 유일하게 쓰지 못한 것이 점검이력이다.

## C. 한국이 가진 것

국토교통부 건축HUB 건축물대장정보 서비스 표제부 응답에 전국 단일 건물 식별자가
들어 있다. 본 출품작에서 실제로 호출해 확인했다.

<mgmBldrgstPk>107814190</mgmBldrgstPk>   <!-- 건축물대장 관리번호 -->

## D. 이 제안이 우리 출품작을 어떻게 바꾸는가

출품작 **불씨예보(K-Firebird)** 는 500m 격자 단위로 화재위험을 예측해 상위 20%
구역으로 실제 화재의 68.5%를 포착한다. 격자에 머문 이유는 건물 단위로 내려갈
키가 없어서다.

건축물대장을 **읍면동 단위**로라도 붙여 노후도 피처를 만들어 측정해 봤으나
개선이 없었다(−0.8%p, 95% 신뢰구간 −2.53 ~ +0.98%p). 읍면동 단위로는 같은 동의
격자가 모두 같은 값이 되어 격자를 가르지 못하기 때문이다. **건물 단위 키가
있어야 풀리는 문제**라는 것을 측정으로 확인했다.
