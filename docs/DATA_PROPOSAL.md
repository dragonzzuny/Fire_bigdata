# 데이터 제안 (제출 양식용)

제6회 소방안전 빅데이터 활용 및 아이디어 경진대회 · 데이터 제안
박용준 (아주대학교 산업공학과 석사과정)

**제안 유형: ☑ 융합 데이터 제안** (2개 이상의 기존·외부 데이터를 결합)

각 항목은 제출 폼에 그대로 붙일 수 있도록 500자 안에서 작성했습니다.
근거가 되는 실측치와 원문 인용은 뒤의 「부록」에 있습니다.

```
소방대상물 통합식별키 데이터셋 (특정소방대상물·화재안전조사·건축물대장 연계)
```

## 데이터 설명

```
특정소방대상물과 화재안전조사, 건축물대장은 같은 건물을 다루면서도 서로 다른 번호를 사용하고 있어 결합되지 않습니다. 이 데이터셋은 그 번호들을 한 줄에 모아 놓은 대조표입니다.

특정소방대상물 한 건마다 소방의 대상물관리번호와 국토교통부 건축물대장 관리번호, 필지고유번호(PNU), 정제한 도로명·지번주소와 좌표를 함께 싣고, 무엇을 근거로 연결했는지와 매칭 신뢰도, 유효 시작일과 종료일도 같은 줄에 기록합니다.

신축과 멸실을 반영해야 하므로 연 1회 이상 갱신하며, 유효기간을 두었기 때문에 특정 시점의 상태를 그대로 되살릴 수 있습니다. 전국을 대상으로 하되 시·도 단위로 나누어 구축할 수 있고, 파일 형태는 CSV입니다.
```

## 융합 대상 데이터 (최소 2개 · 최대 5개)

| # | 데이터명 | 보유기관 |
|---|---|---|
| 1 | 특정소방대상물 현황 | 시·도 소방본부 (플랫폼 개방 중) |
| 2 | 화재안전특별조사(점검이력) | 시·도 소방본부 (플랫폼 개방 중) |
| 3 | 건축물대장 표제부 | 국토교통부 (건축HUB·공공데이터포털 개방 중) |
| 4 | 도로명주소·건물정보 | 행정안전부 (주소기반산업지원서비스) |
| 5 | 화재발생현황 | 시·도 소방본부 (플랫폼 개방 중) |

1~3번이 핵심이며, 4번은 주소 표기를 정규화하는 데, 5번은 결합 결과를
검증하는 데 사용합니다. 다섯 건 모두 이미 개방되어 있고, 없는 것은 이들을
연결하는 식별키뿐입니다.

## 융합 방법

```
연결에 필요한 번호는 각 기관이 이미 보유하고 있습니다. 화재안전조사에는 대상물관리번호가 100% 들어 있고 건축물대장에는 전국 단일 관리번호가 있으나, 정작 특정소방대상물 데이터셋에만 둘 다 없습니다.

1단계는 특정소방대상물에 대상물관리번호 컬럼을 추가하는 작업으로, 소방 내부 자료이므로 신규 수집 없이 점검이력과 결합됩니다.

2단계는 건축물대장 연계입니다. 소방이 보유한 건축물관리번호를 우선 사용하고, 없으면 지번주소를 PNU로 변환해 연결하며, 그래도 남는 건은 행정안전부 주소 API로 도로명을 정규화한 뒤 대조하고, 마지막으로 좌표 근접과 주용도 일치를 확인합니다. 적용한 방법은 행마다 매칭근거 컬럼에 기록합니다.

3단계에서는 화재발생현황으로 결합 결과를 교차 확인하며, 연결하지 못한 행은 비워 둡니다.
```

## 활용 목적 및 활용방안

```
현재는 점검이 화재를 줄이는지 측정할 수 없습니다. 점검이력이 어느 건물의 것인지 특정되지 않기 때문입니다. 연계키가 있으면 점검을 받은 건물과 받지 않은 건물의 이후 화재 발생률을 비교할 수 있으므로, 법정 점검주기를 조정하고 예방 예산의 성과를 설명할 근거가 마련됩니다.

점검 대상을 선정하는 방식도 달라집니다. 지금은 지역 단위로만 위험을 추정하지만, 건물 단위로 내려가면 예측 단위와 점검 단위가 일치하므로 예측 결과를 그대로 점검계획서로 옮길 수 있습니다.

플랫폼이 보유한 유동인구와 화재보험 위험도, 소방IoT 데이터도 같은 키로 대상물에 결합됩니다.
```

## 제안 배경 및 차별성

```
이번 대회 출품작을 개발하다 실제로 막힌 지점입니다. 울산 화재안전특별조사 887,753행에는 대상물관리번호가 100% 들어 있으나 특정소방대상물 데이터셋(컬럼 14개)에는 그 번호도 주소도 없어, 연결할 방법이 없는 채로 88만 행을 사용하지 못했습니다.

애틀랜타 소방의 Firebird와 뉴욕 FDNY의 RBIS도 같은 문제를 겪었습니다. 두 사례 모두 부서 간 공유되는 건물 ID가 없다는 점을 최대 난제로 지목했으며, 주소 문자열 매칭으로 우회한 뒤 그 오차를 한계로 기록했습니다.

미국은 전국 단위 건물 식별자 자체가 없어 우회할 수밖에 없었지만, 한국에는 건축물대장 관리번호가 이미 있습니다. 따라서 새로 수집하자는 제안이 아니라, 각 기관이 가진 번호를 서로 알려 주자는 제안입니다.
```

## 데이터 확보·구축 방안

```
1단계에는 추가 수집 비용이 들지 않습니다. 특정소방대상물 데이터셋에 대상물관리번호 컬럼을 추가하면 되며, 이 번호는 소방이 이미 사용하고 있습니다. 화재안전조사 데이터에 100% 실려 있는 것이 그 근거입니다. 개인정보가 아닌 행정 식별자이므로 개방에도 제약이 없고, 컬럼 하나로 점검이력 88만 행을 사용할 수 있게 됩니다.

2단계인 건축물대장 연계는 국토교통부 건축HUB에서 이미 개방 중인 자료를 사용하며, 건축물관리번호와 PNU 변환, 행정안전부 주소 정규화, 좌표·용도 대조의 순으로 적용합니다.

매칭하지 못한 행은 채우지 않고 비워 둡니다. 억지로 붙인 행이 섞이면 그 데이터로 만든 분석 전체가 의심받기 때문에, 채움률보다 매칭근거를 공개하는 편이 중요합니다.
```

## 기대효과

```
점검의 화재 저감 효과를 측정할 수 있게 되며, 법정 점검주기를 조정하거나 예방 예산의 성과를 설명하고 소방시설 지원 대상을 선정할 때 건물 단위의 근거가 생깁니다.

플랫폼 측면에서는 소방안전 카테고리에 240건이 등록된 반면 화재위험분석은 1건에 그치고 있습니다. 데이터를 새로 추가하기 전에 이미 등록된 240건이 서로 결합되도록 하는 편이 활용도를 더 높입니다. 이용자가 각자 주소를 정제해 매칭하던 작업이 없어지고, 같은 데이터에서 이용자마다 다른 결과가 나오는 문제도 줄어듭니다.

화재보험 요율 산정이나 소방시설 관리업체의 대상물 이력 관리와 같이 플랫폼 외부에서의 활용도 가능해집니다.
```

```
이 제안이 틀릴 수 있는 지점도 밝힙니다. 소방 내부에 건축물관리번호가 없을 수 있으나, 그 경우에도 1단계만으로 88만 행을 사용할 수 있으므로 두 단계를 분리해 제안합니다.
```

## D. 이 제안이 우리 출품작을 어떻게 바꾸는가

출품작 **불씨예보(K-Firebird)** 는 500m 격자 단위로 화재위험을 예측해 상위 20%
구역으로 실제 화재의 68.5%를 포착합니다. 격자 단위에 머문 이유는 건물 단위로
내려갈 식별키가 없기 때문입니다.

건축물대장을 **읍면동 단위**로라도 붙여 노후도 피처를 만들어 측정해 보았으나
개선이 없었습니다(−0.8%p, 95% 신뢰구간 −2.53 ~ +0.98%p). 읍면동 단위로는 같은
동에 속한 격자가 모두 같은 값을 갖게 되어 격자를 구분하지 못하기 때문입니다.
**건물 단위 식별키가 있어야 풀리는 문제**임을 측정으로 확인했습니다.
