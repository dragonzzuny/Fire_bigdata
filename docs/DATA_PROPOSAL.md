# 데이터 제안 — 소방대상물 통합식별키 융합 데이터셋

제6회 소방안전 빅데이터 활용 및 아이디어 경진대회 · 데이터 제안
박용준 (아주대학교 산업공학과 석사과정)

> 이 제안의 모든 수치는 플랫폼에서 실제로 내려받은 파일을 세어 얻은 것이다.
> 재현 명령은 문서 끝에 있다.

---

## 1. 데이터명

**소방대상물 통합식별키 융합 데이터셋** (가칭)
`Fire Safety Object Master Key Dataset`

한 줄 요약: **특정소방대상물 · 화재안전조사 · 건축물대장 · 화재발생현황을
하나의 건물 식별자로 잇는 연계 테이블.**

---

## 2. 데이터 설명

### 구성

기존 데이터를 대체하지 않는다. 기존 데이터셋에 **키 한 벌을 더 실어 주는**
얇은 연계 테이블이다.

| 컬럼 | 설명 | 출처 |
|---|---|---|
| `OJTFT_MNG_NO` | 대상물 관리번호 | 소방 내부(이미 존재) |
| `MGM_BLDRGST_PK` | 건축물대장 관리번호 | 국토부 건축물대장 |
| `PNU` | 필지 고유번호(19자리) | 국토부 |
| `ROAD_ADDR` / `JIBUN_ADDR` | 정제된 도로명·지번 주소 | 행안부 주소 |
| `LON` / `LAT` | 좌표(EPSG:4326) | 주소 기반 산출 |
| `VALID_FROM` / `VALID_TO` | 이 매칭이 유효한 기간 | 구축 시 부여 |
| `MATCH_LEVEL` | 매칭 근거 (관리번호 / PNU / 도로명 / 지번) | 구축 시 부여 |
| `MATCH_CONF` | 매칭 신뢰도 0~1 | 구축 시 부여 |

### 핵심은 두 컬럼

`OJTFT_MNG_NO`(소방)와 `MGM_BLDRGST_PK`(건축)를 한 행에 놓는 것.
이 두 줄이 있으면 지금 못 붙는 자료가 전부 붙는다.

## 3. 활용 목적 및 활용방안

### 3-1. 점검이 화재를 줄이는지 처음으로 측정할 수 있다

지금은 **점검이력이 어느 건물의 것인지 알 수 없어** 점검 효과를 측정할 방법이
없다. 키가 생기면 다음이 가능해진다.

- 점검받은 건물과 안 받은 건물의 이후 화재율 비교
- 지적사항 유형별 시정 후 화재 감소폭
- 점검 주기(1년/2년/3년)별 효과 차이 → **법정 주기의 근거를 데이터로 재검토**

이것은 소방 예방행정에서 가장 답하기 어려운 질문이었다. 예산을 지키는 논리도
여기서 나온다.

### 3-2. 예방점검 우선순위 모델의 정확도가 올라간다

본 대회 출품작 **불씨예보(K-Firebird)** 는 500m 격자 단위로 화재위험을 예측해
상위 20% 구역으로 실제 화재의 68.5%를 포착한다. 격자에 머문 이유는 단 하나,
건물 단위로 내려갈 키가 없어서다.

키가 생기면:
- 격자 → **건물 단위** 예측 (점검 대상이 곧 예측 단위가 된다)
- 노후도·연면적·용도를 건축물대장에서 정확히 (지금은 읍면동 단위로만 붙일 수
  있고, 그렇게 붙였더니 개선이 없었다 — 실측 −0.8%p, 신뢰구간 0 포함)
- 점검이력을 피처로 (Firebird 가 쓴 8개 자료 중 우리가 유일하게 못 쓴 것)

### 3-3. 플랫폼의 다른 데이터가 서로 붙는다

플랫폼에는 이미 좋은 재료가 있는데 서로 못 붙는다.

| 붙이면 되는 것 | 지금 왜 안 되나 | 키가 생기면 |
|---|---|---|
| SK텔레콤 유동인구 × 다중이용업소 | 공간 단위가 달라 근사 결합만 | 건물 단위 노출인구 |
| 한국화재보험협회 음식점 화재위험도 × 특정소방대상물 | 업소 식별자 불일치 | 위험도와 점검이력 대조 |
| 소방IoT·전기IoT × 대상물 | 설치 건물 식별 불가 | 센서 경보와 실제 화재 대조 |
| 재난보험 × 화재발생현황 | 물건 식별 불가 | 손해액과 위험도 검증 |

플랫폼 카테고리 중 **화재위험분석은 데이터가 1건뿐**이다. 새 데이터를 늘리기
전에, 이미 있는 240건이 서로 붙게 하는 편이 값이 크다.

## 4. 제안 배경 및 차별성

### 4-1. 배경: 887,753행이 키 하나 없어 버려진다

본 출품작을 만들며 실제로 막힌 지점이다. 숫자는 모두 실측이다.

| 데이터셋 | 규모 | 문제 |
|---|---|---|
| 울산 화재안전특별조사 | **887,753행** (대상물 관리번호 862,790개) | 이 번호가 **특정소방대상물 데이터셋에 없다** |
| 울산 특정소방대상물 | 34,858행 (컬럼 14개) | 관리번호 계열 컬럼이 `MLNO_YN`(다중이용업소 여부) 하나뿐 |
| 화재안전특별조사 주소 | **없음** | 주소가 없어 좌표·격자 배정 불가 |
| 안전관리등급 `SFTY_MNG_GRD_CD` | 채움률 **0%** | 등급을 여기서도 못 얻는다 |

우리는 이 데이터셋을 **비활성화**했다. 88만 행이 쓰이지 못하고 있다.
(`configs/schema.yaml` 의 `inspection.file_glob` 을 비웠다.)

### 4-2. 국제 사례: 미국도 같은 벽에 막혔고, 풀지 못했다

미국 애틀랜타 **Firebird**(KDD 2016, NFPA 모범사례)와 뉴욕 **FDNY RBIS** 는
이 분야의 대표 사례다. 두 프로젝트가 공통으로 지적한 최대 난제가 이것이다.

> "여러 부서에서 모은 상업용 건물 자료를 결합하기가 어렵다 —
> **공유되는 건물 ID 체계도, 일관된 주소 형식도, 자료를 정확하고 최신으로
> 유지하는 내부 품질관리도 없기 때문이다.**"
> — Firebird / FDNY RBIS 사례 보고

Firebird 는 8개 자료를 결합했는데, 결국 **주소 문자열 매칭**으로 우회했다.
그래서 논문 자체가 매칭 오류를 한계로 적고 있다.

### 4-3. 차별성: 한국은 이미 답을 갖고 있다

**미국이 못 푼 이유는 전국 단일 건물 식별자가 없어서다. 한국에는 있다.**

- 국토교통부 **건축물대장 관리번호**(`mgmBldrgstPk`)는 전국 모든 건축물에
  부여된 단일 키다. 본 출품작에서 건축HUB API 를 호출해 실제로 확인했다
  (예: 울산 남구 삼산동 표제부 응답의 `<mgmBldrgstPk>107814190</mgmBldrgstPk>`).
- 소방에는 이미 **대상물 관리번호**(`OJTFT_MNG_NO`)가 있고 채움률 100%다.
- **둘을 한 행에 놓기만 하면 된다.** 새로 조사할 것도, 새 체계를 만들 것도 없다.

즉 이 제안은 *새 데이터를 만들자*가 아니라 **이미 각자 갖고 있는 번호를
서로 알려 주자**는 것이다. 국제 사례가 못 넘은 벽을 한국은 이미 넘을 조건을
갖추고 있는데, 그 사실이 데이터에 반영되어 있지 않을 뿐이다.

### 4-4. 다른 제안과 다른 점

| 흔한 제안 | 이 제안 |
|---|---|
| 새 데이터를 수집하자 | 이미 있는 키를 실어 주자 (수집 비용 0) |
| 이런 게 있으면 좋겠다 | **88만 행이 못 쓰이고 있다**는 실측 |
| 활용 방안을 상상 | 활용을 시도하다 막힌 기록이 코드와 문서로 남아 있음 |
| 단일 데이터 추가 | 기존 240건이 **서로 붙게** 하는 기반 |

## 5. 데이터 확보 및 구축 방안

### 5-1. 1단계 — 키를 실어 주기만 해도 대부분 해결된다 (즉시, 비용 0)

**특정소방대상물 데이터셋에 `OJTFT_MNG_NO` 컬럼을 추가한다.**

소방 내부 시스템에는 이미 이 번호가 있다(화재안전조사 데이터에 100% 실려
있다는 것이 그 증거다). 개방 시 컬럼에서 빠졌을 뿐이다. 개인정보가 아니라
행정 식별자이므로 공개에 지장이 없다.

이 한 줄로 **점검이력 88만 행이 즉시 살아난다.**

### 5-2. 2단계 — 건축물대장과 잇기 (3~6개월)

| 방법 | 대상 | 예상 매칭률 | 비고 |
|---|---|---|---|
| 소방 내부 대장의 건축물 관리번호 | 신축·허가 동의 대상 | 높음 | 건축허가 동의 시 이미 참조 |
| PNU(필지고유번호) 경유 | 지번주소 보유분 | 중 | 국토부 주소 API |
| 도로명주소 정규화 매칭 | 나머지 | 중 | 행안부 주소기반산업지원서비스 |
| 좌표 근접 + 용도 일치 | 잔여 | 낮음 | 사람 확인 필요 |

**매칭하지 못한 건은 비워 두고 `MATCH_LEVEL` 에 사유를 남긴다.**
억지로 붙인 행이 하나 섞이면 그 데이터로 만든 모든 분석이 의심받는다.
채움률을 높이는 것보다 **어떻게 붙였는지 밝히는 것**이 중요하다.

### 5-3. 3단계 — 시점 관리 (지속)

건물은 신축·멸실·용도변경이 일어난다. `VALID_FROM`/`VALID_TO` 로 이력을
관리해야 **과거 시점 재현**이 가능하다. 이 컬럼이 없으면 "2018년에 이 건물이
있었나"에 답할 수 없고, 시계열 분석이 전부 현재 시점으로 오염된다.

본 출품작이 겪은 문제가 정확히 이것이다 — 대상물·업소 데이터에 시점이 없어
2014년 행에도 2021년 값이 들어간다.

### 5-4. 품질 기준 제안

- 매칭률뿐 아니라 **매칭 근거별 분포**를 함께 공개
- 표본 추출 검증(예: 1,000건 육안 대조) 결과를 명세에 기재
- 갱신 주기와 최종 갱신일 명시

## 6. 기대효과

### 6-1. 정책

- **점검 효과를 처음으로 측정** — 법정 점검주기 조정의 근거
- 예방 예산의 성과를 화재 감소로 설명 가능
- 소화전 신설·설비 지원 대상 선정에 건물 단위 근거

### 6-2. 분석·서비스

- 예방점검 우선순위를 **격자 → 건물 단위**로. 점검 대상이 곧 예측 단위가 된다
- 플랫폼 240건 데이터의 결합 가능성 확대 (유동인구·보험·IoT ↔ 대상물)
- **화재위험분석 카테고리(현재 1건)** 를 실질적으로 채우는 기반

### 6-3. 산업

- 화재보험 요율 산정에 점검이력·건물속성 반영
- 소방시설 관리업체의 대상물 이력 관리
- 스타트업이 결합 가능한 형태의 자료 → 플랫폼 활용도 자체가 올라감

### 6-4. 국제적 위치

Firebird·FDNY 가 지적한 "건물 ID 연계 부재"를 한국이 먼저 해결하면,
**예방점검 우선순위 분야에서 국제적으로 앞선 사례**가 된다. 재현 가능한
데이터 기반이 있는 나라와 없는 나라의 차이는 논문 한 편이 아니라
정책 실행력의 차이다.

## 7. 기타 의견

### 7-1. 이 제안이 틀릴 수 있는 지점

- 소방 내부에 실제로 건축물 관리번호가 없을 수 있다. 그렇다면 1단계
  (`OJTFT_MNG_NO` 추가)만으로도 점검이력이 살아나므로 **1단계와 2단계를
  분리해 제안**한다.
- 매칭률이 낮게 나올 수 있다. 그때는 낮은 채로 공개하고 근거를 밝히는 편이
  낫다. 억지 매칭은 데이터 신뢰를 통째로 무너뜨린다.

### 7-2. 함께 제안하는 작은 개선 (비용이 거의 없다)

본 출품작을 만들며 확인한 것들이다.

| 항목 | 현재 | 제안 |
|---|---|---|
| 화재발생현황 `_2021` 파일 | 시각이 전부 `000000` | 시각 보존 — 시간대 분석이 이 파일에서만 불가능하다 |
| 화재안전조사 `SFTY_MNG_GRD_CD` | 채움률 0% | 채워서 개방 (등급이 곧 위험 신호) |
| 세종 소방용수시설 좌표 | 38건 전부 시 경계 밖 | 좌표 검증 후 개방 |
| 대상물 데이터 | 현재 시점 스냅샷 | 기준일자 컬럼 추가 |
| 데이터셋 파일명 | `_0000` / `_2021` 의미가 명세에 없음 | 누적/최신 구분을 명세에 기재 |

### 7-3. 근거 재현

이 문서의 모든 수치는 아래로 다시 만들 수 있다.

```bash
git clone https://github.com/dragonzzuny/Fire_bigdata
# 플랫폼에서 울산 데이터셋을 data/raw/ulsan/ 에 배치한 뒤
./scripts/run_all.sh
```

- 88만 행 미결합 근거: `docs/DATA_REALITY.md` §10
- 노후도 읍면동 단위 실측(−0.8%p): `outputs/building_feature_eval_ulsan.json`
- 건축물대장 관리번호 확인: `src/firebird/buildings.py`
