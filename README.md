# 불씨예보 (K-Firebird)

한정된 소방 인력으로 **‘어디를·언제’ 먼저 점검·순찰할지** 데이터로 정해 주는 웹 서비스.

제6회 소방안전 빅데이터 활용 및 아이디어 경진대회 — 서비스 개발 부문 (박용준, 아주대학교)

소방안전 빅데이터(울산)로 500m 격자 단위 화재위험을 예측하고,
위험요인(SHAP) · 점검계획서 · 순찰 동선 · 소화전 사각지대를 자동으로 제시한다.

> 이 저장소는 기획서 제출 이후 원본 작업물이 유실되어 **기획서 기준으로 재구축**한 것이다.
> 기획서에 적힌 성능 수치는 원본 데이터를 다시 확보해 `scripts/04_train_eval.py` 를 돌려
> 재현해야 하며, 재현 전까지 이 저장소는 어떤 수치도 주장하지 않는다.
> 진행 상태는 [docs/REPRODUCTION.md](docs/REPRODUCTION.md) 에 기록한다.

## 무엇을 하는가

```
원본 CSV ─▶ 주소 정규화 ─▶ 카카오 지오코딩 ─▶ 500m 격자 ─▶ 격자×연도 패널
                                                              │
                              ┌───────────────────────────────┘
                              ▼
                  LightGBM 위험예측 (시간분할 검증)
                              │
        ┌─────────────┬───────┴────────┬──────────────┐
        ▼             ▼                ▼              ▼
   위험 우선순위   SHAP 요인+규칙    순찰 시간·동선   소화전 사각지대
    (화면1)      → LLM 점검계획서      (화면3)        (화면4)
                   (화면2)
```

**분석 단위가 격자인 이유**: 공개 데이터에 건물번호·좌표가 없다. 주소에서 안정적으로
뽑아낼 수 있는 가장 낮은 해상도가 (시군구·도로명)이고, 이를 500m 격자로 모은 것이
현실적인 최적 단위다. 부산형 상세주소를 확보하면 건물 단위로 내려갈 수 있다.

**위험 판단과 문서 생성을 분리한 이유**: 위험도는 모델이, 점검 항목은 규칙이 정한다.
LLM 은 이미 확정된 입력을 문장으로 옮기기만 한다. LLM 이 점검 항목이나 법령을
지어내면 그건 행정 문서의 오류가 되기 때문이다. 산출물에는 어느 경로로 만들어졌는지가
항상 함께 기록된다 — 사람이 쓴 문서와 기계가 쓴 문서를 나중에 구분할 수 없으면
검수 자체가 불가능하다.

### LLM 백엔드

`configs/config.yaml` 의 `llm.backends` 순서대로 시도하고, 되는 첫 번째를 쓴다.

| 백엔드 | 조건 | 측정 속도 |
|---|---|---|
| `cli` | `llm.cli.command` 의 실행파일이 PATH 에 있을 때 | codex 기준 약 20초/건 |
| `api` | `llm.api.key_env` 환경변수에 키가 있을 때 (OpenAI 호환) | — |
| `ollama` | `localhost:11434` 가 응답할 때 | — |
| `rule_based` | 항상 | 즉시 |

기본값은 `codex exec` 다. 다른 CLI 로 바꾸려면 `command` 만 고치면 된다.
프롬프트는 마지막 인자로 붙고, `{prompt}` 를 쓰면 그 자리에 치환되며,
`prompt_as_stdin: true` 면 표준입력으로 넘어간다.

```yaml
llm:
  backends: [cli, api, ollama, rule_based]
  cli:
    command: ["codex", "exec", "--skip-git-repo-check"]
```

> 확인된 제약: `gemini` CLI 는 개인 티어 지원 종료(`IneligibleTierError`)로 실패한다.

## 빠른 시작

```bash
git clone https://github.com/dragonzzuny/Fire_bigdata
cd Fire_bigdata

python3 -m venv .venv
.venv/bin/pip install -r requirements.txt

cp .env.example .env      # 카카오 REST API 키를 채운다
```

### 1) 데이터 받기
`docs/DATA_SOURCES.md` 의 링크에서 CSV 를 받아 아래처럼 둔다.
플랫폼 로그인 + 무료 주문 절차가 필요하다(자동 다운로드 불가).

```
data/raw/ulsan/    울산 화재발생현황 / 특정소방대상물 / 다중이용업소 / 소방용수시설 / 화재안전특별조사
data/raw/sejong/   세종 화재발생현황 / 특정소방대상물 / 다중이용업소
```

### 2) 파이프라인 실행

```bash
./scripts/run_all.sh
```

또는 단계별로:

```bash
.venv/bin/python scripts/01_inspect_raw.py     # 컬럼이 맞는지 먼저 본다
.venv/bin/python scripts/02_geocode.py         # 카카오 API (느림, 캐시됨)
.venv/bin/python scripts/03_build_dataset.py   # 격자×연도 패널
.venv/bin/python scripts/04_train_eval.py      # 학습 + 3가지 검증
.venv/bin/python scripts/05_artifacts.py       # 현장 산출물
```

### 3) 대시보드

```bash
.venv/bin/streamlit run app/streamlit_app.py
```

## 원본 컬럼이 안 맞을 때

시도별로 컬럼명이 다르다. `01_inspect_raw.py` 가 실제 컬럼과 매칭 결과를 찍어 준다.

```
필수 address        <- '소재지도로명주소'
!! 필수 occurred_at  <- (못 찾음) 후보: ['화재발생일시', '발생일시', ...]
```

`configs/schema.yaml` 의 해당 항목에 **실제 컬럼명을 한 줄 추가**하면 끝난다.
파이썬 코드는 건드리지 않는다.

## 검증 프로토콜

하나만으로는 답이 안 나오므로 셋을 모두 돌린다.

| 프로토콜 | 묻는 것 | 구현 |
|---|---|---|
| 시간분할 홀드아웃 | 미래를 맞히는가 (2020까지 학습 → 2021 예측) | `model.temporal_validation` |
| 시간분할(이력만) | 스냅샷 피처를 빼도 되는가 | `features.history_only_columns` |
| LOGO (구·군 제외) | 한 지역을 외운 것인가, 옮길 수 있는 규칙인가 | `model.logo_validation` |
| 도시 이식 (울산→세종) | 새 도시에서도 되는가 | `model.transfer_validation` |

핵심 지표는 **상위 k% 포착률** — “위험 상위 20% 격자에 점검·순찰을 집중하면
그해 실제 화재의 몇 %가 그 안에서 발생했는가”. 항상 **베이스라인(‘작년에 화재가
많았던 순’)과 함께** 보고한다. 도시 화재는 원래 소수 격자에 몰려 있어서,
베이스라인 없이는 높은 포착률이 잘한 것인지 알 수 없다.

`04_train_eval.py` 는 **단일 피처만으로 줄 세운 결과**도 함께 낸다.
‘대상물 수 하나만 봐도 어느 정도 맞는다’는 한계를 우리가 먼저 숫자로 갖고 있기 위해서다.

## 이 저장소가 스스로 지키는 것

- **누수 차단이 코드로 강제된다.** 연도 t 의 피처는 t-1 까지의 화재만 쓴다.
  `features.assert_no_leakage()` 가 패널을 만들 때마다 실제로 검산하고,
  깨지면 파이프라인이 멈춘다.
- **좌표는 피처가 아니다.** 격자 좌표(gx/gy/lon/lat)를 학습에 넣으면 모델이
  ‘위험한 동네의 위치’를 외워 새 도시에서 무너진다. `features.NON_FEATURE_COLUMNS`
  가 이를 막고, 테스트가 그 사실을 지킨다.
- **화재 0인 격자를 버리지 않는다.** 버리면 포착률의 분모가 실제 도시와 달라진다.
- **동점을 입력 순서로 깨지 않는다.** 베이스라인은 화재 0 격자가 수천 개라
  동점 덩어리가 거대하다. 고정 시드 난수로 깬다.
- **깎여나간 양을 기록한다.** 좌표 확보율, 연도 추출 실패, 격자 배정 실패를
  `manifest_<city>.json` 에 남긴다. 숫자를 못 만든 것과 만들었는데 나쁜 것은 다른 문제다.
  좌표는 lon·lat 이 **둘 다** 있어야 확보로 센다(하나만 있으면 격자에 배정되지 않는다).
- **스냅샷 피처의 시간 누수를 숨기지 않고 잰다.** 대상물·업소·소화전 데이터에는
  '언제부터 존재했는가'가 없어 과거 연도 행에도 현재 값이 들어간다. 데이터로는
  없앨 수 없는 한계이므로, `04_train_eval.py` 가 **이력 피처만으로도 한 번 더 검증**해
  스냅샷이 더한 몫(%p)을 함께 보고한다.
- **검증 실패를 성공처럼 보이게 하지 않는다.** LOGO 에 쓸 폴드가 하나도 없으면
  NaN 을 돌려주는 대신 멈춘다. '검증했는데 결과가 없다'와 '검증을 못 했다'는 다르다.
- **`--no-api` 는 진짜로 네트워크를 끊는다.** 환경변수에 키가 있어도 호출하지 않는다.

## 한계 (기획서 6.기타와 동일)

- 공개 데이터에 건물주소·좌표가 없어 **도로·격자가 해상도 한계**다.
  부산형 상세주소를 확보하면 건물 단위·노후도(사용승인일)로 확장 가능하다.
- **점검 이력은 결합이 불가**했다.
- 특정소방대상물·다중이용업소는 **현재 시점 스냅샷**이라 과거 연도에도 같은 값이 쓰인다.
  연도별 이력이 확보되면 이 부분이 개선된다.
- 순찰 동선은 **직선거리 기준 최근접 연결**이며 도로망 최적 경로가 아니다.

## 라이선스 · 유의

공개 데이터만 사용하며 개인정보를 다루지 않는다(도로·격자 집계 단위).
산출물은 예측 결과이며 법정 점검주기·관할 판단을 대체하지 않는다.
